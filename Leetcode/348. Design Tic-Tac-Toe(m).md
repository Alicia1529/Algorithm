tag: design, matrix, counting

`TicTacToe(n)` then `move(row, col, player)` → the winning player, or `0`. Moves are
always legal and never repeat a cell; a player wins by filling any row, column, or
either diagonal.

### Python — 1. Keep the board, scan the 4 lines through the move

```python
class TicTacToe:

    def __init__(self, n: int):
        self.n = n
        self.board = [[0] * n for _ in range(n)]
        
    def _check_row(self, row, player):
        for col in range(self.n):
            if self.board[row][col] != player:
                return False
        return True
    
    def _check_col(self, col, player):
        for row in range(self.n):
            if self.board[row][col] != player:
                return False
        return True

    def _check_diag(self, row, col, player):
        if row != col:
            return False
        for i in range(self.n):
            if self.board[i][i] != player:
                return False
        return True

    def _check_anti_diag(self, row, col, player):
        if row != self.n - 1 - col:
            return False
        for i in range(self.n):
            if self.board[i][self.n - 1 - i] != player:
                return False
        return True

    def move(self, row: int, col: int, player: int) -> int:
        self.board[row][col] = player
        if self._check_row(row, player) or self._check_col(col, player) or self._check_diag(row, col, player) or self._check_anti_diag(row, col, player):
            return player
        return 0


# Your TicTacToe object will be instantiated and called as such:
# obj = TicTacToe(n)
# param_1 = obj.move(row,col,player)
```

**O(n) per move worst case, O(n²) space.**

The key pruning: only check the lines that *pass through* `(row, col)`. A move can't
complete a row it isn't in, so there are at most 4 candidate lines, never `2n + 2`.

Three details here are the ones people get wrong:

- **The anti-diagonal test is `row == n - 1 - col`**, equivalently `row + col == n - 1`.
  Writing `row + col == n` is the classic off-by-one.
- **The four checks are `or`-ed, not `elif`-chained.** The center of an odd board lies
  on *both* diagonals, so they must be independent.
- **`n == 1`:** the single cell is simultaneously its row, its column, and both
  diagonals. All four checks fire and it correctly returns a win.

> The early `return False` matters more than it looks — see Performance below.

### Python — 2. Don't store the board; store one counter per line

A win means "some line is entirely one player," and a line's state fits in a **single
integer**. Player 1 adds `+1`, player 2 adds `-1`; the line is won exactly when the
counter reaches `±n`.

```python
class TicTacToe:

    def __init__(self, n: int):
        self.n = n
        self.rows = [0] * n
        self.cols = [0] * n
        self.diag = 0
        self.anti = 0

    def move(self, row: int, col: int, player: int) -> int:
        d = 1 if player == 1 else -1
        n = self.n
        self.rows[row] += d
        self.cols[col] += d
        if row == col:
            self.diag += d
        if row + col == n - 1:
            self.anti += d
        if (abs(self.rows[row]) == n or abs(self.cols[col]) == n
                or abs(self.diag) == n or abs(self.anti) == n):
            return player
        return 0
```

**O(1) per move, O(n) space.**

- **`abs()` is mandatory.** Player 2's winning row reads `-n`, not `n`. Comparing
  against `n` alone silently misses every player-2 win — a 3×3 row filled by player 2
  gives `rows[0] == -3`.
- **Why `2n + 2` counters cover everything:** there are exactly `2n + 2` winning lines
  (n rows, n columns, 2 diagonals), so one integer each is the whole win condition.
  The grid was never needed.
- **The `±1` encoding** works whenever there are exactly two categories and the
  question is "are they all the same?" Same trick as balanced-parenthesis counters and
  equal-count subarrays via prefix sums.

### Performance

Measured, `n²` moves with legal alternating play, best of 3 (CPython):

| n | moves | board scan | counters | ratio |
|---|---|---|---|---|
| 50 | 2,500 | 2.86 ms | 1.65 ms | 1.7x |
| 200 | 40,000 | 46.89 ms | 27.53 ms | 1.7x |
| 500 | 250,000 | 345.97 ms | 188.51 ms | 1.8x |

**Only ~1.7x, and flat in `n`** — not the asymptotic blowout "O(n) vs O(1)" implies.
The reason is the early `return False`: with two players alternating, a row almost
always contains an opponent mark or an empty cell within a couple of cells, so the
scan exits immediately. Measured cells probed per move:

| n | avg cells probed | worst case (`2n`) |
|---|---|---|
| 10 | 3.12 | 20 |
| 100 | 2.81 | 200 |
| 500 | 2.77 | 1000 |

So solution 1's "O(n) per move" behaves like O(1) on realistic input.

**The worst case is still legally reachable**, though — one player extends a single
row while the opponent plays elsewhere, and each move rescans the prefix it already
owns: ~`n²/2` probes total (measured 250,498 at n=500, avg 502 per move ≈ `n`).
Removing the early exit entirely (one player, no opponent marks) widens the gap, and
it grows with `n`:

| n | board scan | counters | ratio |
|---|---|---|---|
| 50 | 3.6 ms | 1.5 ms | 2.4x |
| 200 | 64.7 ms | 24.4 ms | 2.6x |
| 400 | 310.4 ms | 106.3 ms | 2.9x |

**Which to use:** solution 1 is readable and the helper decomposition makes each win
condition independently testable — fine as a first answer. But "can you make `move`
O(1)?" is a near-certain follow-up, and solution 2 also drops space from O(n²) to
O(n). Lead with 1 if it's how you think about the board; have 2 ready.

> Minor: `_check_diag(self, row, col, player)` and `_check_anti_diag` take both
> coordinates but only need one after the guard (on the main diagonal `row == col`).
> Harmless, droppable.

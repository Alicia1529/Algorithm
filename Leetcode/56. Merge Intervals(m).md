tag: sort function, overlapping intervals

### Python

**1. Append-and-extend** — build the output list, mutate its last element to grow the
current group.

```python
# Runtime: 136 ms, faster than 5.51% of Python3 online submissions for Merge Intervals.
class Solution:
    def merge(self, intervals: List[List[int]]) -> List[List[int]]:
        intervals.sort(key = lambda x: x[0])
        ans = []
        for interval in intervals:
            if len(ans) == 0:
                ans.append(interval)
                continue
            if interval[0] <= ans[-1][1]:
                ans[-1][1] = max(interval[1], ans[-1][1])
            else:
                ans.append(interval)
        return ans
```

**2. Carry the open group in locals, flush at the end** — hold `interval_start` /
`interval_end` in variables instead of reaching into `ans[-1]`, and emit a group only
when it's closed. The trailing `output.append(...)` is essential: the last group is
still open when the loop ends and nothing else will flush it.

```python
class Solution:
    def merge(self, intervals: List[List[int]]) -> List[List[int]]:
        intervals.sort()
        output = []
        interval_start, interval_end = intervals[0][0], intervals[0][1]
        for start, end in intervals[1:]:
            if interval_end < start:
                output.append([interval_start, interval_end])
                interval_start, interval_end = start, end
            else:
                interval_end = max(interval_end, end)
        output.append([interval_start, interval_end])
        return output
```

Notes on this one:
- **`interval_end < start` is the same test as `start <= interval_end`, negated** —
  the overlap rule of insight 3 is unchanged, just written from the other side.
- **It builds fresh lists**, so unlike solution 1 it does *not* mutate the caller's
  `intervals` (see insight 5). It still sorts in place.
- **`intervals.sort()` sorts by the whole pair**, start then end. Ties on start get
  ordered by end, which changes nothing here — verified identical output to
  `key=lambda x: x[0]` across every case tested.
- **Empty input raises `IndexError`** on `intervals[0]`. LeetCode guarantees
  `n >= 1`; add `if not intervals: return []` if you reuse this.

### C++

```c++
// Runtime: 16 ms, faster than 94.25% of C++ online submissions for Merge Intervals.
// Memory Usage: 14 MB, less than 96.77% of C++ online submissions for Merge Intervals.
class Solution {
public:
    vector<vector<int>> merge(vector<vector<int>>& intervals) {
        vector<vector<int>> ans;
        sort(intervals.begin(), intervals.end(),
            [] (vector<int>& a, vector<int>& b) {
                return a[0] < b[0];
            });
        for (auto& interval: intervals) {
            if (ans.size() == 0) {
                ans.push_back(interval);
                continue;
            }
            if (interval[0] <= ans.back()[1]) {
                ans.back()[1] = max(ans.back()[1], interval[1]);
            } else {
                ans.push_back(interval);
            }
        }
        return ans;
    }
};

            }
```

## Key insights

**1. Sorting by start is what makes one pass enough.** After sorting, any interval
that overlaps the one you're building must overlap it *at the right edge* — every
later interval has a start `>= ` the current start, so there is no way for a future
interval to reach back and connect two groups you've already closed. That's the whole
proof: a closed group stays closed, so you never revisit, and greedy one-pass works.

**2. `max` is mandatory when extending.** `ans[-1][1] = max(interval[1], ans[-1][1])`
— not plain assignment. Sorting by start says nothing about ends, so a fully
**nested** interval arrives with a smaller end and would shrink the group.
Counterexample: `[[0,2],[1,1]]` → assignment gives `[[0,1]]`, correct is `[[0,2]]`.

**3. `<=`, not `<` — touching counts as overlapping.** LeetCode treats `[1,4]` and
`[4,5]` as mergeable into `[1,5]`. Counterexample for `<`: `[[0,0],[0,1]]` →
`[[0,0],[0,1]]` instead of `[[0,1]]`. If a variant defines intervals as half-open
`[start, end)`, flip it back to `<`. **Read the problem statement for this one** —
it's the single most common silent wrong-answer in interval problems.

**4. Sort by start here, but by END for "how many can I keep".** These look alike and
are not interchangeable:
| Problem | Sort key | Why |
|---|---|---|
| 56. Merge Intervals | **start** | build groups left to right; only the right edge matters |
| 57. Insert Interval | **start** (already sorted) | same scan, one new interval |
| 435. Non-overlapping Intervals | **end** | keeping the earliest-ending interval leaves the most room |
| 252/253. Meeting Rooms | **start** (+ min-heap of ends) | sweep the timeline |

> Swapping the two genuinely breaks things in both directions. Sorting 56 by end
> gives `[[0,2],[1,1]]` → `[[1,2]]`. Sorting 435 by start on the canonical
> `[[1,100],[11,22],[1,11],[2,12]]` removes 3 intervals instead of the optimal 2 —
> the greedy grabs `[1,100]` first and it swallows everything.

**5. Solution 1 mutates the caller's input; solution 2 doesn't.** In solution 1
`ans.append(interval)` appends the *same list object*, so `ans[-1][1] = ...` writes
through into `intervals`. After `merge([[1,3],[2,6],[8,10]])` the argument has become
`[[1,6],[2,6],[8,10]]`. Fine on LeetCode; a real bug in library code — append a copy
(`ans.append(interval[:])`) if the caller keeps their list. Solution 2 constructs new
`[interval_start, interval_end]` lists and leaves the elements untouched (it still
reorders `intervals`, since `.sort()` is in place). The C++ copies on `push_back`,
so it's clean too.

**6. Why it's O(n log n) and can't be better.** The sort dominates; the scan is O(n).
Merging intervals lets you detect whether `n` numbers are all distinct, so it inherits
the `Ω(n log n)` comparison lower bound — no clever linear trick exists in general.

> **The reusable shape:** *sort by one endpoint, then sweep, keeping one accumulator
> you either extend or close.* 56 extends the end; 435 counts closures; 253 pushes
> ends into a heap. Recognizing which endpoint to sort by is most of the work.

tag: greedy algorithm

Balloons span `[start, end]`; an arrow at `x` bursts every balloon with
`start <= x <= end`. Find the minimum number of arrows.

### Python

**Greedy — sort by end, shoot at the earliest end**

```python
class Solution:
    def findMinArrowShots(self, points: List[List[int]]) -> int:
        points.sort(key=lambda x: x[1])
        ans = 1
        last_shoot = points[0][1]
        for start, end in points:
            if last_shoot < start:
                last_shoot = end
                ans += 1
        return ans
        # [[1,6],[2,8],[7,12], [10,16]]
        # [1---------6]
        #    [2------------8]
        #              [7----------12]
        #                     [10-----------16]
```

O(n log n) time (the sort), O(1) extra space.

**Why sort by end:** once you commit to shooting a balloon, the arrow should go as
far *left* as still bursts it — at its end. That position is the greediest possible:
it bursts the current balloon plus every other balloon that reaches at least that far.
Sorting by end means the first unburst balloon you meet always has the smallest end
among what remains, so its end is the optimal next arrow. Sorting by **start** breaks
this — a balloon that starts early but ends very late would claim an arrow far to the
right and waste it.

In the diagram: sorted by end, `[1,6]` comes first → arrow at **6**, which also
bursts `[2,8]`. Next unburst is `[7,12]` (since `6 < 7`) → arrow at **12**, which also
bursts `[10,16]`. Two arrows.

> **`ans = 1` with the loop starting at index 0 is correct, not off by one.** The
> first iteration re-examines `points[0]`, but `last_shoot` is already `points[0][1]`
> so `last_shoot < start` is false — it can never double-count. The `1` accounts for
> that first arrow. (LeetCode guarantees `points` is non-empty; on `[]` this raises
> `IndexError` at `points[0][1]`.)

> **`<` not `<=`:** touching balloons share an arrow — `[1,6]` and `[6,9]` are both
> burst by an arrow at 6. Using `last_shoot <= start` would count 2. Same trap as
> [56. Merge Intervals](<56. Merge Intervals(m).md>).

**Relationship to [435. Non-overlapping Intervals](<435. Non-overlapping Intervals (m).md>):**
same sort key and same sweep — 452 counts the groups it forms (arrows), 435 counts
what it discards. But they are **not** simply `n` minus each other, because the two
problems disagree on touching intervals:

- 452: `[1,2]` and `[2,3]` share an arrow at `x = 2` → **1** arrow.
- 435: `[1,2]` and `[2,3]` don't overlap → **0** removals, so `n - 0 = 2 ≠ 1`.

That's the `s > end` vs `s >= end` boundary. Force both to the same rule and the
identity `arrows == n - removals` does hold exactly (verified on 2,023 cases) — but
with each problem's actual rule it fails on 798 of them. Same skeleton, different
question; don't port the comparison operator between them.

### C++

```c++
// Runtime: 132 ms, faster than 59.18% of C++ online submissions for Minimum Number of Arrows to Burst Balloons.
// Memory Usage: 34.7 MB, less than 99.60% of C++ online submissions for Minimum Number of Arrows to Burst Balloons.
class Solution {
public:
    int findMinArrowShots(vector<vector<int>>& points) {
        sort(points.begin(), points.end(), [](const vector<int>& v1, const vector<int>& v2) {
            return v1[1] <= v2[1];
        });
        int end = -1;
        int ans = 0;
        for (int i = 0; i < points.size(); i++) {
            if (end < 0 || end < points[i][0]) {
                ans++;
                end = points[i][1];
            }
        }
        return ans;
    }
};
```
> ⚠️ **`return v1[1] <= v2[1];` is a bug** — `std::sort` requires a *strict weak
> ordering*, meaning the comparator must return `false` for two equal elements. With
> `<=` it returns `true`, and libstdc++/libc++ can then run the partition pointer off
> the end of the array: undefined behavior, sometimes a segfault. It passed here by
> luck. Use `return v1[1] < v2[1];`.
>
> Also note this version initializes `end = -1` and guards with `end < 0`, which
> assumes coordinates are non-negative — LeetCode allows `-2^31`. Tracking a
> `bool first` or using `LLONG_MIN` is safer. The Python version sidesteps both
> issues by seeding from `points[0][1]`.

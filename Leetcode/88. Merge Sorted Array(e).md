## Python — fill from the back, O(m+n) time / O(1) space

**Key trick:** `nums1` has `n` spare slots at the end, so write the **largest**
element into the back and walk both pointers backward. Filling back-to-front means
you never overwrite a `nums1` value you haven't read yet.

```python
class Solution:
    def merge(self, nums1: List[int], m: int, nums2: List[int], n: int) -> None:
        """Do not return anything, modify nums1 in-place instead."""
        i, j, k = m - 1, n - 1, m + n - 1   # tails of nums1, nums2, and the write head
        while 0 <= i and 0 <= j:
            if nums1[i] < nums2[j]:
                nums1[k] = nums2[j]; j -= 1
            else:
                nums1[k] = nums1[i]; i -= 1
            k -= 1
        while 0 <= j:                        # drain leftover nums2 into the front
            nums1[k] = nums2[j]; j -= 1; k -= 1
```

**Complexity:** O(m+n) time, O(1) extra space.

---

## Key insights

**1. The spare slots ARE the answer.** `nums1` is handed to you with length `m + n`
— the `n` trailing zeros are not padding to work around, they're the scratch space
that makes O(1) merging possible. Whenever a problem hands you an oversized buffer,
ask what it wants you to write there.

**2. Fill backward, because the write head can never outrun the read head.**
The invariant is `k >= i` at every write:
```
k - i = (m + n - 1 - #writes) - (m - 1 - #reads_from_nums1)
      = n - (#writes - #reads_from_nums1)
      = n - #reads_from_nums2  >=  0
```
Every write consumes exactly one element from one of the two arrays, so `k` falls at
the same rate as `i` and `j` *combined* — it can only pull ahead of `i` alone. So
`nums1[k]` is always a slot whose original value is already read or was empty to
begin with. Forward filling has no such guarantee and corrupts immediately:
`[1,2,3] + [1,2,3]` forward-fills to `[1,1,1,1,0,0]` — the write head laps the read
head at the very first tie.

**3. Only one drain loop is needed, and it's the `nums2` one.** If `nums1` empties
first, leftover `nums2` values still have to be moved. If `nums2` empties first, the
remaining `nums1` values are *already sitting in their final positions* — every
element that belonged after them has been placed above, and nothing displaced them.
Adding the symmetric `while 0 <= i` loop isn't wrong, just a no-op copying each
element onto itself. Verified: harmless, but noise.

**4. The tie-break doesn't matter for correctness.** `<` vs `<=` in the comparison
both produce the correct sorted output (checked exhaustively). It only decides
*which* equal element lands first — relevant if you ever extend this to a stable
merge over tagged records, irrelevant for plain ints.

**5. Edge cases fall out for free.** `m == 0` → the first loop never runs, the drain
loop copies all of `nums2` down. `n == 0` → both loops skip and `nums1` is untouched.
No special-casing needed; the C++ `if (n == 0) return;` guard above is an
optimization, not a requirement.

> **The generalization:** this is the merge step of merge sort, and it's why "merge
> two sorted things" problems (21. Merge Two Sorted Lists, 23. Merge k Sorted Lists,
> 977. Squares of a Sorted Array) all reduce to two pointers walking inward or
> outward. 977 is the same backward-fill trick: largest square is at one of the two
> ends, so fill the result from the back.

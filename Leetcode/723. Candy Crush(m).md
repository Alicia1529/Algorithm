**Simulation, four phases in a loop:** find → crush → drop → repeat until stable.

- **Key insight:** collect all cells to crush into a **set** first, THEN crush — a cell
  can belong to both a horizontal and a vertical match, and crushes must happen
  *simultaneously*, not greedily. The set dedupes overlaps for free.
- **Gravity:** per column, walk bottom-up with a `last_row` write pointer, copying
  non-zero values down, then zero-fill the top. Standard two-pointer compaction.
- O((m·n)²) worst case (each pass O(m·n), up to m·n passes), O(m·n) space.

### Python

```python
class Solution:
    def find_candidates(self, board, candidates) -> bool:
        found = False
        # horizontal 3-in-a-row
        for i in range(self.m):
            for j in range(1, self.n - 1):
                if board[i][j] == 0:
                    continue
                if board[i][j - 1] == board[i][j] == board[i][j + 1]:
                    found = True
                    candidates |= {(i, j - 1), (i, j), (i, j + 1)}
        # vertical 3-in-a-row
        for i in range(1, self.m - 1):
            for j in range(self.n):
                if board[i][j] == 0:
                    continue
                if board[i - 1][j] == board[i][j] == board[i + 1][j]:
                    found = True
                    candidates |= {(i - 1, j), (i, j), (i + 1, j)}
        return found

    def crush_candies(self, board, candidates):
        for x, y in candidates:
            board[x][y] = 0

    def drop_candies(self, board):
        for col in range(self.n):
            last_row = self.m - 1
            for row in range(self.m - 1, -1, -1):     # bottom-up
                if board[row][col] != 0:
                    board[last_row][col] = board[row][col]
                    last_row -= 1
            while last_row >= 0:                       # zero-fill the top
                board[last_row][col] = 0
                last_row -= 1

    def candyCrush(self, board: List[List[int]]) -> List[List[int]]:
        self.m, self.n = len(board), len(board[0])
        while True:
            candidates = set()
            if not self.find_candidates(board, candidates):
                return board                          # stable → done
            self.crush_candies(board, candidates)
            self.drop_candies(board)
```

- The `set` is the crux: without it, crushing greedily as you scan would corrupt
  overlapping horizontal/vertical matches. Find *all* first, then crush together.
- The `board[i][j-1] == board[i][j] == board[i][j+1]` chained compare is Python
  shorthand for both equalities (and it short-circuits).

## Run-length 写法（扫段，而不是扫固定窗口）

上面那版用固定 3 格窗口判断三连。另一种写法是**走完整段**（run-length），好处是能
直接拿到真实段长 —— 要改成「消除 4 连以上」只改 `>= 3` 这一个数字，固定窗口写法
得整段重写。

```python
class Solution:
    def candyCrush(self, board: List[List[int]]) -> List[List[int]]:
        m, n = len(board), len(board[0])

        def find_candidates():
            candidates = set()
            # 横向
            for row in range(m):
                col = 0
                while col < n:
                    v = board[row][col]
                    if v == 0:
                        col += 1
                        continue
                    k = col + 1
                    while k < n and board[row][k] == v:
                        k += 1
                    if k - col >= 3:
                        candidates.update((row, j) for j in range(col, k))
                    col = k                      # ← 跳过整段
                    
            # 纵向
            for col in range(n):
                row = 0
                while row < m:
                    v = board[row][col]
                    if v == 0:
                        row += 1
                        continue
                    k = row + 1
                    while k < m and board[k][col] == v:
                        k += 1
                    if k - row >= 3:
                        candidates.update((i, col) for i in range(row, k))
                    row = k                      # ← 跳过整段
            return candidates

        def drop():
            for col in range(n):
                last_row = m - 1
                for row in range(m - 1, -1, -1):
                    if board[row][col] != 0:
                        board[last_row][col] = board[row][col]
                        last_row -= 1
                while last_row >= 0:
                    board[last_row][col] = 0
                    last_row -= 1

        while True:
            candidates = find_candidates()
            if not candidates:
                return board
            for row, col in candidates:
                board[row][col] = 0
            drop()
```

### ⚠️ `col = k` 是关键，不能写 `col += 1`

run-length 有个容易踩的坑：如果每个格子都起一次 run-walk（`col += 1`），同一段会被
**重复走 L 次**：

```python
# 退化写法 —— 从每个起点都重走一遍
for col in range(n):
    k = 1
    while k + col < n and board[row][col] == board[row][col + k]:
        k += 1
```

遇到 `aaaa`：从 col 0 走 4 步、col 1 走 3 步、col 2 走 2 步…… 总计 `1+2+…+n = n²/2`。

| 写法 | 单轮复杂度 | 全同行 n=1000 实测步数 |
|---|---|---|
| 固定 3 格窗口 | `O(m·n)` | 1,996 |
| run-length **+ `col = k`** | `O(m·n)` | **1,000** |
| run-length + `col += 1` | `O(m·n·L)`，最坏 `O(m·n²)` | **500,500** |

`L` = 最长连续段长度。`col = k` 保证每格只访问一次，复杂度回到 `O(m·n)`，同时保留
段长信息。

### 但实际上几乎不影响速度

`L` 在真实盘面上是个小常数，不是 `n`。80×80 全程观测到的最大段长：

| 不同数值个数 | 观测到的最大 L |
|---|---|
| 2 | 15 |
| 3 | 12 |
| 5 | 8 |
| 10 | 6 |

所以端到端只快约 **1.05x**（200×200：398ms → 383ms），冗余内层步数虽然砍掉一半
（79,985 → 40,000）却换不来多少真实收益。

> 注意：长段**不是只有第一轮才出现**。下落会把相同值重新堆成长段 —— vals=2 时
> L=15 出现在第 2 轮，而不是第 1 轮。所以不能假设「消除一次之后段长就 ≤ 2」。

**真正的开销在轮数**：每轮都要全盘重扫，100×100 要 6–18 轮。单轮时间分布实测
mark 占 55–77%、drop 占 23–45%、crush 不到 2%。所以优化方向应该是「少扫几轮」，
而不是「单轮扫得更快」。

### 试过但不值得的优化

都量测过，结论记在这里免得重复试：

| 方案 | 结果 |
|---|---|
| 去掉 set，原地取负标记 | **0.91–1.01x**，没变快（set 不是瓶颈） |
| run-length 跳段 | 冗余步数减半，端到端 **1.05x** |
| 微调内层循环（局部变量、行别名、切片 drop） | **0.97–1.20x** |
| dirty row/column 增量重扫 | 1.5–1.9x，但**错 1074/5000 组** ❌ |

dirty-tracking 在本题上**理论上就不成立**：下落会把方块搬到任意行，新的横向匹配可以
出现在任何位置，「脏区域」几乎等于整盘。1.5x 换高正确性风险，不划算。

### 另外两点代码质量

- **`candidates` 不要放在外层当共享闭包变量**。如果 `find` 靠 `if candidates:` 判断
  是否有匹配，就隐式依赖 `crush` 把它 pop 干净 —— 两个函数通过一个 set 耦合。目前
  这样写是安全的（实测 651 次调用，进入时永远是空的），但哪天在 crush 前加个提前
  `return` 就会静默出错。改成局部变量 + 返回值（如上），耦合消失，空 set 自带
  falsy 语义。
- **调试用的 `print_board()` 记得删**。

> 里的 `k` 是同一个套路：从一端往另一端搬有效值，剩下的补默认值。

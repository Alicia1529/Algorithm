tag: intervals, greedy

Insert `newInterval` into a list of **non-overlapping, start-sorted** intervals,
merging as needed. The input being pre-sorted is the whole point — it's what
separates this from [56. Merge Intervals](<56. Merge Intervals(m).md>).

### Python

**Method 1 — one pass, carry the growing interval**

Classify every existing interval against the one being inserted: entirely before,
entirely after, or overlapping. The `new_start/new_end` pair absorbs every overlap;
the `elif` branch flushes it once you're safely past.

```python
class Solution:
    def insert(self, intervals: List[List[int]], newInterval: List[int]) -> List[List[int]]:
        output = []
        new_start, new_end = newInterval
        for start, end in intervals:
            # current interval is completely before newInterval
            if end < new_start:
                output.append([start, end])
            # current interval is completely after newInterval
            elif new_end < start:
                output.append([new_start, new_end])
                new_start, new_end = start, end
            # otherwise they overlap
            else:
                new_start = min(new_start, start)
                new_end = max(new_end, end)
        output.append([new_start, new_end])
        return output
```

> **The trick in the `elif`:** after flushing, it reassigns `new_start, new_end =
> start, end` — the *current* interval becomes the new "pending" one. That's what
> lets a single trailing `append` handle every case, and why the rest of the list
> falls through the same branch cheaply.

**Method 2 — three explicit phases**

Say out loud what the loop does: copy everything before, merge everything touching,
copy everything after. No classification per element, just three walks.

```python
class Solution:
    def insert(self, intervals: List[List[int]], newInterval: List[int]) -> List[List[int]]:
        output = []
        i = 0
        # before
        while i < len(intervals) and intervals[i][1] < newInterval[0]:
            output.append(intervals[i])
            i += 1
        # overlapping
        start, end = newInterval[0], newInterval[1]
        while i < len(intervals) and intervals[i][0] <= newInterval[1]:
            start = min(start, intervals[i][0])
            end = max(end, intervals[i][1])
            i += 1
        output.append([start, end])
        # after
        while i < len(intervals):
            output.append(intervals[i])
            i += 1
        return output
```

> Note the two loop conditions are **not** symmetric: phase 1 tests
> `intervals[i][1] < newInterval[0]` (an interval's *end* vs the new *start*), phase 2
> tests `intervals[i][0] <= newInterval[1]` (an interval's *start* vs the new *end*).
> Getting either boundary backwards is the classic bug here.

**Method 3 — append, sort, then run Merge Intervals**

Don't solve the problem; reduce it to one you've already solved.

```python
class Solution:
    def insert(self, intervals: List[List[int]], newInterval: List[int]) -> List[List[int]]:
        intervals.append(newInterval)
        intervals.sort()
        output = []
        output.append(intervals[0])
        for start, end in intervals[1:]:
            if output[-1][1] < start:
                output.append([start, end])
            else:
                output[-1][1] = max(output[-1][1], end)
        return output
```

> Throws away the sortedness you were handed, which is why it's asymptotically worse.
> But it's ~8 lines you already know cold, and in an interview "I'd reduce this to 56"
> is a perfectly good first answer before you optimize. Note it mutates the caller's
> `intervals` (appends *and* sorts in place), and aliases `intervals[0]` into the
> output.

### Performance

| | Time | Space | Mutates input |
|---|---|---|---|
| **M1** one pass | O(n) | O(n) output | no |
| **M2** three phases | O(n) | O(n) output | no (copies refs) |
| **M3** append + sort | O(n log n) worst / O(n) here | O(n) | **yes** — appends and sorts in place |

All three are one linear pass in practice; the interesting part is *why* the measured
numbers don't match the big-O ranking.

Measured on `n` disjoint intervals `[3i, 3i+1]`, best of 3–5 runs (CPython):

| n | scenario | M1 | M2 | M3 |
|---|---|---|---|---|
| 10,000 | new at front | 2.07 ms | 1.62 ms | 4.55 ms |
| 10,000 | new at end | 1.76 ms | 2.33 ms | 4.10 ms |
| 10,000 | new spans all | 3.51 ms | 4.95 ms | 4.51 ms |
| 100,000 | new at front | 34.60 ms | 16.39 ms | 79.85 ms |
| 100,000 | new at end | 26.65 ms | 22.75 ms | 73.86 ms |
| 100,000 | new spans all | 35.27 ms | 50.88 ms | 56.66 ms |
| 100,000 | new in middle | 32.75 ms | 19.36 ms | 64.20 ms |

**M2 beats M1 despite identical O(n).** M1 evaluates a two-branch classification for
*every* interval, even the thousands that are trivially before or after. M2's phase-1
and phase-3 loops do one comparison (or none) and an append. Same complexity,
noticeably less work per element.

**M1 wins when the new interval spans everything.** Then M2's phase-2 does `min`+`max`
per element while phase 1 and 3 do nothing — it degenerates into a slower version of
M1's overlap branch.

**M3's cost is NOT the sort.** I assumed it would be and measured: at n=100,000 the
`.sort()` is only ~3 ms of the ~75 ms total — **7%**. Timsort detects the input is
already sorted except for one appended element and finishes in essentially O(n). The
real cost is the Python-level scan touching all n+1 intervals with a branch and a
`max` each. So M3 is ~2–3x slower for the boring reason: more bytecode per element,
not the asymptotics.

**The big win is letting C do the copying.** Phases 1 and 3 are just "copy a
contiguous run", which slicing does at C speed:

```python
class Solution:
    def insert(self, intervals: List[List[int]], newInterval: List[int]) -> List[List[int]]:
        n = len(intervals)
        i = 0
        while i < n and intervals[i][1] < newInterval[0]:
            i += 1
        j = i
        start, end = newInterval
        while j < n and intervals[j][0] <= newInterval[1]:
            start = min(start, intervals[j][0])
            end = max(end, intervals[j][1])
            j += 1
        return intervals[:i] + [[start, end]] + intervals[j:]
```

| scenario (n=100,000) | M2 while-loops | M2 with slices |
|---|---|---|
| new at front | 13.38 ms | **0.72 ms** |
| new in middle | 16.04 ms | **6.35 ms** |
| new at end | 19.36 ms | **12.36 ms** |
| new spans all | 44.77 ms | 41.71 ms |

Up to **18x faster**, same O(n) — the index scan still walks every element, but the
copying moves into C. When the new interval overlaps everything there's nothing to
slice, so the gain vanishes. Verified identical output to M2 on all 3,696 test cases.

**Going further: binary-search the boundaries.** Both phase-1 and phase-2 loops are
just "find the first index where a monotone condition flips" — that's a binary search.
Combined with slicing, nothing Python-level touches more than `O(log n)` elements:

```python
class Solution:
    def insert(self, intervals: List[List[int]], newInterval: List[int]) -> List[List[int]]:
        n = len(intervals)
        start, end = newInterval
        lo, hi = 0, n                      # first interval whose end >= start
        while lo < hi:
            mid = (lo + hi) // 2
            if intervals[mid][1] < start: lo = mid + 1
            else: hi = mid
        i = lo
        lo, hi = i, n                      # first interval whose start > end
        while lo < hi:
            mid = (lo + hi) // 2
            if intervals[mid][0] <= end: lo = mid + 1
            else: hi = mid
        j = lo
        if i < j:                          # something overlapped — absorb the run
            start = min(start, intervals[i][0])
            end = max(end, intervals[j - 1][1])
        return intervals[:i] + [[start, end]] + intervals[j:]
```

| scenario (n=100,000) | M2 slice | binary search |
|---|---|---|
| new at front | 0.92 ms | 0.97 ms |
| new in middle | 6.51 ms | **1.14 ms** |
| new at end | 11.71 ms | **0.98 ms** |
| new spans all | 45.72 ms | **0.03 ms** |

Essentially flat regardless of where the interval lands. The `spans all` case is the
striking one — 45.72 ms → 0.03 ms, because the two searches immediately collapse to
`i=0, j=n` and both slices are empty. Still `O(n)` overall (the slices copy), but the
constant is a C `memcpy` instead of a Python loop. Verified against M1 on all 3,696
cases.

> Only the two `min`/`max` reads are needed after the search — `intervals[i][0]` and
> `intervals[j-1][1]` — because the run `[i, j)` is contiguous and sorted, so the
> extremes are at its ends. That's the same reasoning as the second C++ solution
> below, which uses `lower_bound`/`upper_bound` and splices in place.

**Interview takeaway:** M1 or M2 is the expected answer, and either is fine. M3 shows
you recognized this is 56 in disguise. Bring up binary search only if pushed on
optimizing — it's a real win, but the copy keeps it `O(n)` on paper, so it reads as
over-engineering unless you're asked.



### C++

```c++
// Runtime: 32 ms, faster than 37.77% of C++ online submissions for Insert Interval.
class Solution {
public:
    vector<vector<int>> insert(vector<vector<int>>& intervals, vector<int>& newInterval) {
        int idx = 0;
        for (int i = 0; i < intervals.size(); i++) {
            if (newInterval[0] > intervals[i][0]) {
                idx++;
            } else {
                break;
            }
        }
        intervals.insert(intervals.begin() + idx, newInterval);
        vector<vector<int>> ans;
        for (auto &interval: intervals) {
            if (ans.size() > 0 && interval[0] <= ans.back()[1]) {
                ans.back()[1] = max(interval[1], ans.back()[1]);
            } else {
                ans.push_back(interval);
            }
        }
        return ans; 
    }
};


#include<vector>
using namespace std;
#define pb push_back
class Solution {
public:
    bool does_overlap(vector<int> interval, int s, int e)
    {
        return !(e<interval[0] || s>interval[1]);
    }
    vector<vector<int>> insert(vector<vector<int>>& intervals, vector<int>& newInterval) {
        int s = newInterval[0], e = newInterval[1];
        vector<int> a; a.pb(s); a.pb(INT_MAX);
        vector<vector<int>>::iterator left = lower_bound(intervals.begin(), intervals.end(), a);
        a.clear(); a.pb(e); a.pb(INT_MAX);
        vector<vector<int>>::iterator right = upper_bound(intervals.begin(), intervals.end(), a);
        if(left!=intervals.begin() && does_overlap(*(left-1), s, e))
            left--;
        int new_left = s, new_right = e;
        if(left<right)
        {
            new_left = min(new_left, (*left)[0]);
            new_right = max(new_right, (*(right-1))[1]);
        }
        intervals.erase(left, right);
        vector<int> temp; temp.pb(new_left); temp.pb(new_right);
        intervals.insert(left, temp);
        return intervals;
    }
};
```
